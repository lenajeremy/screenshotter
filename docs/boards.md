# Boards

A board is a design canvas made of real HTML and CSS, in the spirit of [Paper](https://paper.design): pages of artboards, each a tree of layers (frames, text, images, vectors) with its own CSS. People draw and edit on it in the Studio; agents write HTML onto it through the MCP, and the person watches the design come together. The point: an agent can prototype a screen or a flow, and you see it before anything is built.

- **Masks** (15 November, "done properly and fully, as Figma does them, but in real HTML and CSS"): a layer with `mask` ("alpha", "vector" or "luminance") isn't drawn; the layers above it in its frame (after it, up to the next mask) show only where it is. Hiding the mask shows them whole.
  - **In HTML** (`maskCss`, `childrenHtml` in the core; the canvas draws the same through `MaskScope`): the mask stays, hidden, with `data-mask`; what it masks goes in two elements after it, one over the frame (`position:absolute; inset:0`, `data-mask-scope`) so the layers keep their left and top, and one on the mask's box (static, so it never becomes what they're placed in) with the mask's look: a frame's fills as `mask-image` layers with `mask-mode`, its corners as `clip-path: inset(0 round …)` (a vector mask is the clip-path alone), a picture as `url()` sized by its object-fit, an svg as its SVG in a data: URL (vector: every painted pixel solid, through a filter), words as an SVG holding their own HTML and CSS in a foreignObject (so they wrap as on the canvas), its opacity as one more layer intersected over the rest. `-webkit-` spellings too.
  - **Words:** an SVG drawn as an image can't load fonts, so `loadMaskFonts` fetches a text mask's Google font (only the faces its words need) into it, in the Studio and before the engine draws (exports, thumbnails, screenshots, Preview). The Mac's own fonts need nothing; offline, a web font draws in the next font of its list.
  - **Studio:** Use as mask (⌃⌘M, the layer menu, the panel's Mask section, Edit › Use as Mask); several layers become a "Mask group" on the mask's box, the one at the back masking the rest. The panel: Alpha / Vector / Luminance, on/off, what it masks; a masked layer says which mask. The layer list marks the mask and joins it to its layers; the canvas outlines the mask over a picked or hovered layer it masks.
  - **Agents:** `data-mask` in board_write_html; board_edit `mask` (make, change, group, remove); board_read marks masks and what they mask; a CSS `mask-image` over layers placed by hand comes in as a mask layer (over flowing layers it stays CSS).
  - **Tests:** the core, the tools and a screenshot's pixels in `test:board`; three `test:ui` checks in both engines, with pixels on the canvas, in an export and in Preview (luminance by a gradient and by a photo, and a mask over a group with a mask of its own, among them).
  - **Engines:** `mask-mode: luminance` works in WebKit (the canvas; it also takes `-webkit-mask-source-type`) and in Chromium (exports), for gradients and pictures alike, so a luminance mask is written as CSS like the rest. A mask's `mask-image` and `clip-path` cover the masks inside the layers it masks too: they nest.
  - **Limits:** a mask's rotation, blur and border don't count (its box, fills, corners and opacity do); a frame used as a mask masks by its own fills, not the layers inside it; a mask picture from another site needs CORS (CSS masks are fetched that way); a luminance mask with several fills takes each fill's brightness by itself and adds them (CSS), where Figma takes the brightness of the fills together (a light fill under a dark gradient shows everything).

- **Shaders** (16 November, "live GPU graphics as a layer, presets or the agents' own"): a `shader` layer is a box like any other (size, place, corners, opacity, blend, rotation, masks, components, copy and paste, undo, the Scale tool) drawn live by a WebGL fragment shader. It plays on the canvas and in Preview; pictures (screenshots, exports, thumbnails) show it frozen at its `time`.
  - **The model** (`src/board/shaders.ts`, pure, re-exported by the core and served as `/ui/shaders.js`): a layer's `shader` is a preset (built in, or one of the board's own in `board.shaders`) or GLSL of its own, `params`, `speed`, `time` (the still) and `paused`. Ten presets: mesh gradient, grain gradient, liquid chrome, dither, halftone, light rays, waves, aurora, contours, film grain (see-through, blended as Overlay). Each is written as an agent would write one: parameters are uniforms with a comment (`// @param 0..2 = 0.9`, `// @param 4..40 = 11 px` for a length in design px, `// @color = #ff5a1f`, `// @choice soft|hard = soft`), which the panel turns into controls. Values are made safe (numbers clamped, colours only CSS colours or `var(--token)`, choices one of their words); code is printable ASCII, at most 20,000 characters, and only ever goes to the GPU.
  - **In HTML**: `<div data-shader="mesh-gradient" data-params='{…}' data-speed data-time data-paused><canvas></canvas></div>` (a div, so it's sized and laid out like a frame: `inset:0` and stretching work); `data-shader="custom"` with `data-code`. `<canvas data-shader>` and code in a `<script type="x-shader/x-fragment">` inside it come in the same way. With `code: true` (pages that play it) each carries its GLSL and its uniforms.
  - **The runtime** (`src/studio/ui/board-shader-runtime.js`, a plain script setting `BoardShaders`): one WebGL context for every shader on a page (browsers allow about 16), drawn into a hidden canvas a layer at a time and copied into each layer's own 2D canvas, so CSS does the rest. Layers off screen aren't drawn (IntersectionObserver); while the view pans, zooms or a layer is resized they're drawn at half resolution; never more than 2 pixels per CSS pixel while playing. Reduce Motion makes every shader a still. Colours that are tokens are resolved where the layer is (its computed custom properties). Code that fails to compile draws an error card (the line and message) instead.
  - **Not all at once** (0.15.2, after a board of eight shader frames made the Studio crawl): the shaders on screen don't all play. Every few frames the runtime ranks the ones that would play: the one being worked on (the selection, a tile under the pointer: `focus`, `always`) first, then by area on screen. The first plays; the next ones play while their pixels fit `pixelBudget` (4.5 million a frame) and there are fewer than `maxPlaying` (4); one smaller than `minPlaySide` (120 CSS px) on screen holds. A held one keeps the frame it's at and carries on from it when it plays again (state `held`). Playing ones are drawn at `fps` (30): they move slowly. So a whole page in view is a set of stills, and a section in view plays its own.
  - **The frame-time guard**: now and then (on its first frames, then about every half second) a layer's draw is timed to the end by reading one pixel back. Twice over the budget (24 ms) and it's drawn at 0.6, then 0.3, of its size; still too slow and it stops at its still (drawn sharp once), says so on the layer and in the panel, and toasts once. All layers together over 1.5 × the budget gives the costliest a strike. Play (Try again) clears it.
  - **Everywhere the same script**: the Studio imports it; Preview and the pages behind pictures carry it as their first script (`shaderScript` in `render.ts`); pictures call `BoardShaders.ready()`, which draws each layer once at its time before the screenshot, so stills are exact. Copy as HTML puts it first too. Headless Chrome may fall back to SwiftShader (`--enable-unsafe-swiftshader`) where there's no GPU.
  - **A frame's fill** (since 0.15.2): a shader belongs to a frame, as Paper has it, not to a layer of its own. It's drawn on a canvas that is the frame's first child, over the frame's box and behind its layers (`z-index: -1` in the frame's own stacking context: `isolation: isolate`, and `position: relative` when it has no place), so a shader frame is laid out like any frame (a grid cell, an item in a stack) and holds words and pictures over its shader. It's drawn over the frame's CSS fills; `blend` (data-blend) mixes it with them (film grain as Overlay over a photo fill). A frame with nothing else in it is what a shader layer used to be; boards from before (type `shader`) open with each a frame with its shader (`upgradeBoard`, when a board is read).
  - **Studio**: Fill › the shader button (or the shader's row) opens **Choose shader**: every preset's still in a grid, playing under the pointer, a search, the board's own presets and **Your own code**; a pick keeps it open to try another, and it sits clear of the frame it changes. Under the row are the shader's colours (with the board's tokens); **Shader settings** (the sliders tile) holds the rest: its other controls, speed, play/pause, the still's moment and **Now**, blend, Edit code or its GLSL field (compiled as it's typed, errors listed by line, a click selects the line), Save as preset, Reset. Assets › Shaders: a click with a frame selected makes it that frame's fill; with nothing selected, or dragged, it adds a frame of its own. Studied first on Mobbin: Framer's Liquid Gradient section (colours, then label · value · slider rows), Squarespace's background art (Motion with a speed choice), Framer's Loop effect (play or pause off screen), and Bolt's and Retool's error boxes (the line named, a red edge).
  - **Agents**: `board_edit` `shader` (give a frame one with `id`, or add a new frame with one; change its preset, code, params, speed, time, paused or blend; `remove`; `savePreset`, `deletePreset`); shaders in `board_write_html`; `board_read` `shaders` lists every preset's params and the tree describes each layer; own code is compiled in headless Chrome by the same runtime and errors come back with their lines (`shaderErrors` from board_write_html, `errors` from board_edit). The instructions say when to use one and how to write one (GLSL ES 1.00 or 3.00, `uTime`, `uRes`, `uPx`, Shadertoy's `mainImage`).
  - **Tests**: the model, parameters, sanitising, HTML in and out, undo, components, scale, compile errors by line (GLSL 3.00 too), tokens, and pixels (not blank, the same at the same time, another time another picture, 2×) in `test:board`; seven `test:ui` checks in both engines (from Assets with one WebGL context and no component drawn per frame, half resolution while panning, a parameter changing pixels, pause and Reduce Motion, a masked shader, the guard and code errors, resize/rotate/scale, Preview and a copied page playing), with pictures in both themes.
  - **Limits**: a shader draws its own picture; it can't take the layers below it as input (a halftone of a photo needs the photo's pixels in WebGL, which CSS can't give). A shader used as a mask masks with nothing (its pixels aren't known to CSS). No mouse or scroll input yet. GLSL 3.00 needs WebGL 2. There's no HTML file export: Preview and Copy as HTML are the pages that play.

**Decisions:**

- Shaders draw into a 2D canvas per layer from one shared WebGL context, rather than one context each (browsers cap them, and the oldest is lost) or one canvas over the whole board (which would break the order of layers, masks, rotation and blending). The copy costs a GPU blit per layer per frame.
- A shader's element is a frame holding the canvas, not the canvas itself: a canvas is a replaced element (it doesn't stretch to `inset:0` or a grid cell, and its pixel size would feed back into its layout). The canvas is placed out of the frame's flow, so the frame's layout, padding and layers are its own.
- A shader is a fill rather than a layer (0.15.2): as a layer it couldn't hold anything, so text over a moving gradient took a shader placed by hand behind it, and it couldn't simply be a grid cell's or a stack item's background.
- Masks in flex and grid frames: a mask's box has to be known from its CSS (the element that masks sits there), and a layout places its items where CSS can't say. So a mask and what it masks are placed by hand; in a flex or grid frame, Use as mask puts them in a mask group (a frame laid out by hand) that is one item of the layout, as a Figma mask group is in auto layout. A mask an agent leaves in a layout's flow draws but is flagged (board_read, and a warning from board_write_html).

- The design is HTML and CSS, not a vector format. The browser engine does the layout, the text and the drawing, an agent writes it fluently, and code comes out of it nearly as is.
- Tool names start with `board_` because they share the server with 30 other tools. Edits are batched in `board_edit` to keep the tool count down.
- The Studio and agents both write the file on disk under a lock. An agent's change reaches the open board by polling (every 700 ms), and undoing it replaces the whole board.
- Components: the Studio expands its own changes (so a change to a component shows in its copies straight away) and sends the result. The server expands only agents' changes, so nothing is expanded twice.
- An SVG's parts are layers, not one piece of markup, so they can be picked and changed one at a time (as in Paper). Parts can only sit in a vector and nothing else can go in one; one with more than 800 parts stays one piece.
- Only the person resolves a comment: they asked, so they say when it's done (the user's call, 12 November).
- Blue is for selection only, as in the rest of the Studio; everything else on boards is neutral. On 11 November the user compared lime for selection and chose blue (lime is hard to see on light designs and already marks agent work).
